# INDRA — Deployment

## Local, no Docker (fastest)

```bash
cd backend && pip install -r requirements.txt
FRONTEND_DIST=../frontend uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## Docker Compose

```bash
docker compose up --build
```

Starts `frontend` (nginx, port 3000), `backend` (FastAPI, port 8000),
`postgres` (with PostGIS), `redis`, `redpanda`, and `minio`, all with
health checks. The backend runs in **Demo Mode** by default even inside
Compose (no `DATABASE_URL` set) — uncomment the Live Mode env vars in the
`backend` service block to point it at the real Postgres/Redis instead.

**Honesty note:** this compose file has not been executed end-to-end in
the environment this project was built in (no Docker daemon available
there — see `docs/LIMITATIONS.md`). It was reviewed for correctness and
its component pieces (the Dockerfiles, the entrypoint script's migration
logic, the Postgres+PostGIS setup, Redis rate limiting) were each
individually verified working against real local installations of those
services outside of Docker. If `docker compose up --build` surfaces an
issue, please file it.

## Live Mode (real Postgres + PostGIS), manually

This exact sequence was run and verified during the upgrade audit:

```bash
# 1. Install (Ubuntu/Debian)
apt-get install postgresql postgresql-contrib postgis postgresql-16-postgis-3

# 2. Start and create the database
service postgresql start
su postgres -c "psql -c \"CREATE USER indra WITH PASSWORD 'indra_dev_password' SUPERUSER;\""
su postgres -c "psql -c \"CREATE DATABASE indra OWNER indra;\""
su postgres -c "psql -d indra -c \"CREATE EXTENSION IF NOT EXISTS postgis;\""

# 3. Migrate (empty database -> full schema, including PostGIS geometry
#    columns + GIST spatial index)
cd backend
export DATABASE_URL="postgresql+psycopg2://indra:indra_dev_password@localhost:5432/indra"
alembic upgrade head

# 4. Seed and run
python -c "from app.seed import run_seed; run_seed()"
FRONTEND_DIST=../frontend uvicorn app.main:app --host 0.0.0.0 --port 8000
```

`GET /api/health` reports `"mode": "LIVE (Postgres)"` when this worked.

## Migrations

```bash
cd backend
alembic upgrade head        # apply all migrations
alembic downgrade -1        # roll back one
alembic revision --autogenerate -m "description"   # generate a new one after a model change
```

Two migrations exist:
1. `92ad302abd39_initial_schema.py` — the full relational schema
   (autogenerated from `models.py`, reviewed).
2. `b1c2d3e4f5a6_add_postgis_geometry_columns.py` — adds `geom
   geometry(Point,4326)` to `reports` and `events`, a GIST index on each,
   and backfills from existing lat/lng.

`migrations/env.py` filters out PostGIS's own internal bookkeeping
tables (`spatial_ref_sys` etc.) from autogenerate comparisons — without
this, `--autogenerate` tries to drop them, which would break the
extension (a real issue hit and fixed while setting this up).

## Environment variables

See `.env.example` for the full list with inline documentation. Nothing

## Redis

```bash
apt-get install redis-server
service redis-server start
export REDIS_URL="redis://localhost:6379/0"
```
Used for rate limiting (`INCR`+`EXPIRE` per client IP) when set; falls
back to an in-memory limiter if unset or unreachable, so it's never a
hard dependency.

## Not available in this project's build environment (documented, not hidden)

- **Kafka/Redpanda** and **MinIO** — neither ships as an Ubuntu apt
  package, and their binary distributions are not reachable from a
  sandboxed environment restricted to package-registry mirrors. The
  in-process pub/sub bus (`realtime/pubsub.py`) and local-disk object
  storage (`storage.py`) are the tested Demo Mode substitutes; the code
  has clearly marked swap points for real Kafka/Redpanda clients and a
  real S3-compatible client, but those specific integrations have not
  been run against live instances.
